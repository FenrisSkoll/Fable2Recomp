# NR0B-2 recorder design

The original design was recorded before implementation. This correction keeps
its observation points and hard limits while replacing repeated decision-local
state with bounded immutable definitions and durable control transitions.
ReXGlue remains the only renderer. This observer is default-off and
Windows/D3D12 scoped. Metadata is not replay data. No title caller, material,
character, producer or allocation lifetime is inferred from a consumer thread,
pointer, address or shader hash.

## Minimum observation chain

| Observation | Fields and the decision they support |
|---|---|
| Common type-3 dispatch before size/predicate filtering | Run-local decision ID, opcode, predicate and explicit result: count attempted work without treating successful returns as host draws |
| Common decoded draw and D3D12 IssueDraw | Primitive/index source/count/range, query state; distinguish rejection, no-op, copy, unavailable pipeline, preparation failure and main host command |
| Selected shaders and ConfigurePipeline result | Stage, existing XXH3-64 microcode identity/length, analysis availability, selected specialization, run-local pipeline handle and readiness: choose tractable shader pairs without reading shader bytes |
| Accepted render-target update and fixed function state | EDRAM base/pitch/samples, color/depth format, masks, blend/depth/stencil, viewport/scissor: identify required initial contents and output semantics |
| Used shader fetches and texture cache | Requested decoded fetch/view state and observed prepared/null state, only used slots; actual sampler parameters: identify resource needs and uncertainty across preparation failures |
| Resolve after existing GetResolveInfo | Source EDRAM, destination address/extent/layout/sample choice, clear intent and return/written range: identify aliases and GPU-produced inputs without new guest reads |
| Deferred command list operation methods | One record per draw/dispatch/copy/clear/query command, joined to current decision and submission; auxiliary operations remain distinct from the main guest draw |
| BeginSubmission / EndSubmission / CheckSubmissionFence | Existing current/completed IDs, ExecuteCommandLists and Signal result: distinguish recording, issuing and observed completion without additional waits |
| Consumer XE_SWAP entry | Boundary serial and frontbuffer metadata; initial partial interval ends at first observed boundary, then three complete boundary-to-boundary intervals end at the fourth. A consumer boundary is not a displayed frame |

No recurring presenter-thread observation is necessary for the first census;
reuse NR0B-1's configuration context and retain displayed-frame joins as unknown.
No resource producer/lifetime recorder, new page watch, shader analysis or hash
calculation is introduced. Numeric state fields are individually decoded;
raw packets, register arrays and payloads are excluded.

## Ordering, compact state and carry-in

One GPU consumer owns event order, decision context and immutable state
publication. Sequence IDs are serialized record IDs. Every admitted decision,
outcome, resolve, deferred host operation, native execution, submission,
completion and swap remains an individual ordered record.

`REXMETA2` interns the already-decoded state families. The first exact
`(event type, field count, fields)` value is emitted with decision zero; its
record sequence is its run-local definition ID. Later equal values reuse it.
FNV-1a 64 chooses a fixed open-addressed lookup slot, followed by exact equality
checking, so a collision cannot merge different values. Hashes, pointers and
guest addresses do not become resource-lifetime identities.

Each decision accumulates the definition IDs generated by its original state
observation calls. The recorder publishes a bundle in consecutive records of at
most 23 IDs, then one decision-local bundle reference. An exact bundle list may
reuse its immutable first-record ID. The reference is emitted before the main
draw, or before the outcome on a path with no main draw. This preserves the
relative point at which preparation completed while reducing both records and
bytes. Definitions precede first use; definitions and referenced bundles are
never changed, overwritten or evicted.

The first applicable decision publishes definitions for the state it observes,
including state established before STARTED. This is carry-in observation, not a
producer claim. Missing before-window state, absent stages, not-applicable paths
and unobserved preparation remain distinct. An interrupted decision has an
explicit open edge, not a fabricated outcome. If a new definition and its
required bundle/reference transaction cannot fit, admission stops before an
unknown reference can be published and the terminal reports loss.

The worker owns trigger, monotonic deadline, status and serialization. It never
reads GPU objects. Stop uses atomics and a producer publication handshake;
serialization begins only after recording is disabled and an in-flight append
has finished. No recorder lock, I/O or wait belongs on the consumer path.

## Trigger, state history and cues

Launch explicitly supplies a unique run ID and a nonexistent capture output
directory. Existing output roots are refused. A worker registers Ctrl+Shift+F10
(trigger) and Ctrl+Shift+F11 (cancel), with repeat suppression. READY is
published only after both registrations succeed. Messages apply only while
Windows reports this process in the foreground. Registration conflict is an
observer error, never permission to target another process. No network listener
or hot-path file polling is used. The foreground check proves only the accepted
message-time PID, not continuous focus.

The durable transition order is READY, STARTED and one final STOPPED, CANCELLED
or ERROR state. STARTED is published exactly once after an accepted F10; the
five-second deadline begins at that accepted trigger before transition output or
sound. STOPPED is published only after recording ends and `metadata.bin` closes
successfully. CANCELLED remains distinct and ERROR replaces successful STOPPED
when initialization, recording or flushing fails.

Each transition is an atomically renamed JSON record under `transitions`, keyed
by a monotonic sequence and carrying run/PID, recorder monotonic time, a nearby
wall/monotonic correlation sample, foreground/trigger evidence, terminal reason,
flush result and bounded error text. The helper drains every unseen sequence;
a fast capture can pass through STARTED and STOPPED between 250 ms polls without
losing either. `status.txt` is only a compatibility view.

Wrong-foreground or repeated control input may publish a bounded advisory
REJECTED transition without changing recorder state. Space for STARTED and the
final transition is reserved ahead of advisory records.

Worker-only audible cues are distinct: READY has two rising tones, STARTED one
high tone, STOPPED three rising tones, CANCELLED two falling tones and ERROR
three falling tones. Cue failure leaves the durable evidence intact and never
blocks the GPU consumer. The launcher continues monitoring the actual process
until the user exits normally.

## Bounds and failures

Ceilings: five seconds from trigger (steady clock), three complete consumer
intervals, 20,000 decisions, 100,000 records including framing/terminal, 32 MiB
including framing/terminal. The first applicable ceiling stops acceptance.
The deadline worker expires without subsequent GPU events; each append also
checks the deadline. A terminal record and file header are reserved in advance.
Fixed-size decoded records and preallocated storage enforce a stricter memory
bound where needed. The 25,600,000-byte record allocation, fixed 131,072-entry
definition table, fixed 32,768-entry bundle table, 512-ID decision workspace,
fixed bookkeeping and bounded transition history are checked together against
32 MiB. Standard thread stack, bounded paths and C library buffering are
reported separately. No wraparound, eviction or expanding queue is permitted.

Bounded recording may stop mid-decision/submission. Terminal counters preserve
reason, observations, bytes/high-water, rejection/loss and timing; unresolved
edges are explicit. Flush occurs in the worker after the observation window.
Writer/allocation/trigger failure disables the observer; it does not catch a
renderer exception, modify return values or terminate healthy gameplay. Abrupt
process exit may leave missing output/footer and must fail structural validation.

## Acceptance

Synthetic recorder and independent parser fixtures cover default-off, trigger
identity/repetition/foreground checks, READY ordering, delayed transition replay,
idle deadline, exact capacities/reserved footer, collision-safe immutable state,
dictionary exhaustion, swap counting, carry-in/references, all result categories,
auxiliary operations, partial submissions, cancellation, writer failure and
shutdown. A representative dense fixture must retain every decision and
one-to-many relationship and reach at least one complete interval below all
unchanged bounds. Release builds, existing configuration/NR0A/GPU checks and
fresh-session preservation preflight precede the manual run. Synthetic timing
and capacity are not gameplay overhead or runtime-equivalence claims. Actual
capture validity, interval coverage, dependency completeness, gameplay, visual
correctness and disturbance are reported separately. At most one ordinary
indexed/textured candidate is considered; unresolved dependencies are acceptable.
